# Регламент Code Review і QA у PythonStart

## Перед відкриттям Pull Request

1. Укажіть Issue, очікувану поведінку та спосіб її перевірки.
2. Для дефекту зафіксуйте запуск тестів на базі, додайте перевірку, що відтворює помилку, і повторіть повний `npm test` після виправлення.
3. Заповніть чекліст PR і призначте незалежного рецензента, коли він доступний.

## Що перевіряє рецензент

| Критерій | Дія |
| --- | --- |
| Читабельність | Перевірити назви, межі відповідальності, дублювання та необґрунтовані константи. |
| Безпека | Простежити шлях даних від вводу до DOM. Використовувати `textContent` для звичайного тексту. Перевірити, що у змінах немає токенів, паролів чи приватних ключів. |
| Крайові випадки | Перевірити порожні запити, зайві пробіли, невалідні аргументи та пошкоджений JSON у сховищі. |
| Тести | Перевірити, що новий тест відтворює сценарій з Issue і весь набір проходить. |

Зауваження до конкретної зміни залишайте на відповідному рядку у **Files changed**. Поясніть, за яких умов виникає проблема, і наведіть пропозицію або спосіб перевірки. **Comment** підходить для уточнення, **Request changes** для дефекту або відсутності потрібної перевірки, **Approve** для змін, готових до інтеграції. Перед злиттям у `main` потрібні успішні тести і схвалення незалежного рецензента.

## Реєстрація дефектів

Для Issue з міткою `bug` укажіть оточення, кроки відтворення, фактичний та очікуваний результати, виконавця і milestone. Картку додайте на дошку проєкту.

| Параметр | Рівні | Як вибрати |
| --- | --- | --- |
| Severity | Critical, Major, Minor | Оцініть вплив на функції, дані й безпеку тренажера. |
| Priority | High, Medium, Low | Визначте терміновість щодо релізу. |

Під час виправлення використовуйте статус **In progress**, після передачі змін на перевірку **In review**. Після злиття у `main` запустіть регресійний набір і перевірте закриття Issue та статус **Done**.
